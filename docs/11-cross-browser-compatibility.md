# Cross-Browser Compatibility: Firefox to Chrome H.264 Streaming

This document details two critical bugs discovered when attempting to stream H.264 video from a Firefox Broadcaster to a Chrome Viewer via WebTransport, and how they were resolved.

## 1. WebTransport Path MTU Hardcoding Bug

### The Problem
Historically, the `gawk-app` packetizer hardcoded `MAX_DATAGRAM_SIZE` to 1200 bytes. This worked perfectly in Chrome, which reliably negotiates a WebTransport maximum datagram size of `1200+` bytes.
However, Firefox's WebTransport implementation (especially over loopback and IPv6) conservatively limits datagrams to **1024 bytes** (`wt.datagrams.maxDatagramSize = 1024`).

When Firefox acted as a broadcaster, it blindly chunked its keyframes into 1200-byte datagrams. Because these datagrams exceeded the path MTU negotiated by the browser, Firefox's WebTransport layer silently dropped them. As a result, the viewer's `Reassembler` would never receive all the chunks for the keyframe, preventing the video from ever starting.

### The Fix
The `packetizeFrame` function in `packetizer.ts` was updated to accept an optional `maxDatagramSize` argument. The broadcaster now dynamically passes `this.wt?.datagrams.maxDatagramSize` down to the packetizer.

The packetizer ensures that the chunk payload never exceeds this dynamic limit. Thus, when Firefox negotiates a 1024-byte path MTU, it safely breaks the frames into smaller chunks, avoiding dropped packets entirely. The `gawk-server` continues to relay these without issue, as it only enforces `MaxDatagramSize = 1200` as an upper limit.

## 2. Firefox WebCodecs AVCC "Double NALU Type" Bug

### The Problem
When Firefox successfully transmitted a keyframe (either a small one that naturally bypassed the MTU issue, or after the MTU fix), Chrome's `VideoDecoder` would immediately crash with an `EncodingError: Decoding error.`

Inspection of the `extradata` (the `AVCDecoderConfigurationRecord`) generated by Firefox's `VideoEncoder` revealed a severe binary formatting bug in Firefox's H.264 implementation:

1. **Invalid Reserved Bits:** Bytes 4 and 5 were written as `0x03` and `0x01`. The ISO/IEC 14496-15 AVCC specification strictly mandates that the top bits of these bytes be set to 1 (`0xFF` and `0xE1`). Chrome's hardware/software decoders strictly validate these bits and reject the config if they are zeroes.
2. **Double-Byte Shift Bug:** Firefox accidentally duplicated the NALU type byte at the beginning of the Sequence Parameter Set (SPS) and Picture Parameter Set (PPS) payloads inside the `extradata`.
    - Expected SPS start: `67 4d 40 34` (NALU type 7, Main Profile, Compat 0x40, Level 5.2).
    - Firefox SPS start: `67 67 4d 40 34`.
    - This duplication pushed the true `profile_idc` (`0x4D`) to the third byte. Chrome's parser mistakenly read the second `67` (`0x67` = 103) as the `profile_idc`, interpreting the stream as **High Profile**. Since the negotiated codec string was Main Profile (`avc1.4D4034`), Chrome correctly threw a Profile/Level mismatch error and halted decoding.

### The Fix
A `normalizeAvccExtradata` interceptor was added to `viewer.ts` to execute immediately before applying the configuration to Chrome's `VideoDecoder`.

This normalizer dynamically rebuilds the AVCC block from scratch:
1. It applies bitmasks to correctly set the reserved bits in bytes 4 and 5.
2. It parses the SPS and PPS lengths. If it detects a NALU type byte duplication (e.g., `naluData[0] === naluData[1] && naluData[2] === extradata[1]`), it strips the erroneous duplicate byte and decrements the length headers accordingly.

With this dynamically scrubbed `extradata` block, Chrome flawlessly accepts Firefox's encoded H.264 stream.
